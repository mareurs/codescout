# Cross-Harness Background Continuation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver codescout background-job events to their originating Claude Code or Codex conversation through shared, recoverable delivery policy, with native Windows validation and future Pi/Copilot adapters left separate.

**Architecture:** codescout keeps producing schema-1 outcome records. A Node ESM companion engine consumes normalized watches, while harness adapters own identity, hook registration and continuation. A small Python stdlib helper serializes receipt transactions with native OS locks; no new daemon or database is introduced.

**Tech Stack:** Node ESM and `node:test`; Python stdlib locking and JSON files; `ws` 8.22.0 for the Codex WebSocket transport (published version checked with `npm view ws@8 version --json` on 2026-10-30); existing Claude hooks and Codex app-server JSON-RPC. New-engine runtime target: Node 24+ and Python 3.13+ (planner's choices; probe both before activation). The existing legacy hook keeps its current runtime requirements.

**Spec:** [Approved design](../specs/2026-10-30-cross-harness-background-wake-design.md), approved 2026-10-30. Read it alongside this plan.

## Global Constraints

- “The server remains the sole writer of job outcomes.” Keep schema 1 and the existing spawn response unchanged in this increment.
- “A single registered job has one originating target; this is not a fan-out API.” No peer-message or model-text target registration.
- “No platform/harness combination becomes advertised as supported until an end-to-end native test passes.” Native Windows and WSL are separate rows; no Windows/WSL bridging.
- “A timeout or disconnection after sending is unknown unless the adapter can prove non-acceptance.” No exactly-once claim or blind replay.
- “Opt in per profile to a single owner for new jobs: legacy Claude hook or new engine, never both.” Existing watched jobs stay with the old implementation.
- “No product implementation” of Pi/Copilot in this plan. No remote delivery, central daemon, new database, dependency installation, profile changes or release as an incidental test action.
- Work in isolated checkouts of both repositories at execution time. `CS` means `/home/marius/work/claude/codescout`; `CP` means `/home/marius/work/claude/claude-plugins`. Paths below are relative to those checkout roots, not cache installs.
- Run each repository's own required checks. Commit explicit paths only, with native `Session-Id`, and preserve peers' edits. No inline plugin version bump; installation/release is a separate operator action through CP's documented release flow.

## Review Focus

1. Two profiles share a checkout and both have `@bg_00000001`: results reach only the originating profile/server/session. Tests: Tasks 2 and 6.
2. A watcher loses its lease just before send: its expired token must never authorize another send or erase the successor's state. Tests: Task 3.
3. The host accepts a message but the watcher crashes before saving the reply: restarting must expose uncertainty and suppress automatic retransmission. Tests: Tasks 3, 4 and 6.
4. Windows has spaces/non-ASCII paths, a different hook shell, or no Python: startup reports the exact missing capability without falling back to a shell or another profile. Tests: Tasks 1, 3 and 7.
5. A read rearms a heartbeat while another observer sees terminal completion: heartbeat deduplication cannot consume the terminal event. Tests: Tasks 4 and 5.

## Shared interfaces and planner choices

Define these JSDoc types in `model.mjs`; later tasks import the same names rather than inventing parallel shapes:

- `JobRef = {recordPath, schema:1, serverPid, serverToken, handle}`. `recordPath` is canonicalized from the supplied response path. Extract/validate the generation token only against the measured record-name format and check record PID/handle agreement; an unknown format is unsupported, not guessed.
- `TargetBinding = {harness, profileRoot, hostInstanceId, environmentId, sessionId, runtimeGeneration, origin:'root'}`. `harness` is `claude-code|codex`. Store no endpoint credentials here. The adapter receives a configuration reference separately.
- `WatchRequest = {version:1, job:JobRef, target:TargetBinding, sourceEventId}`.
- `DeliveryEvent = {version:1, eventId, kind:'terminal'|'heartbeat'|'tracking-lost', job, target, sequence, payload}`. `payload` holds only the outcome summary/duration/reason, never stdout, full commands or tokens.
- `Capability = {supported:boolean, reason:string, evidenceRef:string|null}`.
- `Receipt = {version:1,event:DeliveryEvent,state,attemptId,ownerToken,leaseUntilMs,lastEvidence,lastError,updatedAtMs}`. States are the spec's `pending|claimed|sending|accepted|continuation_observed|completed|unknown|unsupported|failed`. Claim/retry metadata is optional before a claim.
- `ReceiptStore.transact(command):Promise<{ok:boolean,receipt:Receipt|null,reason:string}>`; `command={op,eventId,nowMs,event?,ownerToken?,attemptId?,leaseMs?,evidence?,result?}`. Discriminant `op` is `ensure|claim|renew|begin-send|evidence|release|recover|gc`; `ensure` requires `event`; `claim` requires fresh `ownerToken`, `attemptId` and `leaseMs`; `renew` requires current `ownerToken`, `attemptId` and `leaseMs`; `begin-send`/`release` require current `ownerToken` and `attemptId`; `evidence` requires matching `attemptId` and either host evidence or a classified delivery `result`. `recover` and `gc` use the stored state and `nowMs`, never a caller-supplied replacement receipt. All mutations run under the helper's persistent per-event lock. Only a stored definite pre-send failure may be reset for the next bounded retry; late evidence must match the persisted event/attempt correlation. Release clears ownership without erasing the outcome or send intent.
- `HostAdapter = {capability(request):Promise<Capability>, validateTarget(request):Promise<Capability>, deliver(event,onEvidence,signal):Promise<DeliveryResult>, close():Promise<void>}`. Evidence is `{state:'accepted'|'continuation_observed'|'completed',eventId,attemptId,correlation}`. `DeliveryResult` is `{kind:'pre-send-failure'|'emitted-unconfirmed'|'unknown'|'finished',reason}`.
- `runWatch(request,{store,platform,adapter,clock,signal,policy}):Promise<WatchResult>`, where result carries `{state,eventId,reason}` and never implies host acknowledgement just from a successful process exit.

Defaults copied from current behavior: poll 1000 ms, record-creation grace 5000 ms, heartbeat deadline 1800 s capped at 7000 s below the 7200 s Claude hook timeout. New planner choices: lease 30 s, renew every 10 s, pre-send retry delays 1/2/4 s with at most three retries; do not sleep through a closed/invalid binding. Make these explicit injectable policy values, not empirical performance claims. Persist heartbeat sequencing separately from the terminal event key.

For GC, retain completed receipts at least seven days after completion; do not automatically GC pending, sending, accepted-but-unconfirmed or unknown receipts. Expose manual retention/reconciliation instructions. This costs state growth until unresolved events are addressed. The claim is process-crash recovery on tested local filesystems, not machine-power-loss durability or network-filesystem safety.

Python is a planner implementation choice for OS-backed, serialized compare-and-update operations without native Node addons. Missing Python disables the new engine, not the legacy path. Python does not deliver messages or become a daemon. See stdlib [Windows locking](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking) and [Unix locking](https://docs.python.org/3/library/fcntl.html#fcntl.flock); platform tests remain mandatory.
