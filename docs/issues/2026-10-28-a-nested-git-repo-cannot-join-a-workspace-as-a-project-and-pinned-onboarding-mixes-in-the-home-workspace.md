# BUG: a nested or sibling git repo cannot join a workspace as a project, and onboarding under a workspace pin mixes in the home workspace

## Summary
We keep two small git repos (Python Kodi add-ons, no build manifest) inside a Kodi checkout and want to onboard, index and search them from the Kodi session while each keeps its own git history and remote. No supported mechanism does this: `[[project]]` entries in `.codescout/workspace.toml` are written but never loaded, discovery needs a build manifest, and `onboarding(workspace=<nested repo>)` writes the home workspace's project list into the nested repo.

## Class fit
`[[project]]` entries with an `id`, `root` and `languages` are declared in workspace.toml and checked by doctor (src/librarian/tools/doctor.rs:3229-3243), yet no loader path reaches them, so the declaration reads as a feature and does nothing. Differs from the class's other members: the declaring file is also generated by the same tool, so a user who copies its format has no signal that hand-added entries are inert.

## What we want
- A supported way to name a project root explicitly (manifest-less, inside or beside the workspace, possibly in its own git repo) so it gets a `project_id` for `onboarding`, `index`, `semantic_search`, `memory` and `symbols`.
- Membership independent of git visibility: a directory hidden from the parent repo with `.git/info/exclude` should still be addable.
- Each member keeps its own git identity: its own `git_sync` / `last_indexed_commit`, its own commits.
- `onboarding` (and any tool) with `workspace=<abs path>` writes only that directory's own state.
- No new tracked files in the parent repo. The Kodi repo is third-party and its AGENTS.md discourages unrelated changes.

## Symptom (Effect)
After adding two `[[project]]` entries to the Kodi workspace file, `workspace(action="list_projects")` still returned the original five projects. Observed after a re-activation, after `/mcp` reconnect, and after a full Claude Code restart.

`onboarding(workspace="<kodi>/remote-fixes/script.module.thecrew")` returned the Kodi workspace instructions (`"Onboarding required — this is a workspace with 5 projects."`, prompts for kodi, xbmc, addons, libUPnP, packaging) and created `<repo>/.codescout/` containing a `workspace.toml` with `name = "script.module.thecrew"` but the five Kodi `[[project]]` entries, plus a `project.toml` with `model = "local:JinaEmbeddingsV2BaseCode"` while the Kodi session uses `CodeRankEmbed` (source: env). It also appended `.codescout/private-memories/` to the repo's tracked `.gitignore`.

## Reproduction
Codescout server build `f9b0fc9f8` (from `workspace(status)`, before the restart). Active project: a Kodi checkout, workspace of 5 auto-discovered projects.
1. `mkdir <kodi>/remote-fixes` and put two git repos there (Python add-on files, no pyproject.toml, setup.py, requirements.txt or other manifest at their roots).
2. Add them to the exclude file: `echo '/remote-fixes/' >> <kodi>/.git/info/exclude`.
3. Add to `<kodi>/.codescout/workspace.toml`:
   ```toml
   [[project]]
   id = "thecrew-module"
   root = "remote-fixes/script.module.thecrew"
   languages = ["python"]
   depends_on = []
   ```
4. `workspace(action="activate", path="<kodi>")`, then `workspace(action="list_projects")`. The new id is absent.
5. `onboarding(workspace="<kodi>/remote-fixes/script.module.thecrew")` and read the new `.codescout/workspace.toml` there.

## Environment
Linux, Claude Code, codescout over MCP, remote-http embedding backend (CodeRankEmbed), Kodi checkout on branch master. Two add-on repos with `core.autocrlf false`.

## Root cause

Two causes, both verified by reading the code and by a test that failed first.

1. **Declared members were never loaded.** `discover_projects` builds the list by walking for manifests (Cargo.toml, CMakeLists.txt, build.gradle(.kts), go.mod, pom.xml, mix.exs, Gemfile; and package.json with scripts, pyproject.toml, setup.py, requirements.txt) using `ignore::WalkBuilder` with `.hidden(true)` and `.git_ignore(true)`. `read_discover_settings` read only `discovery_max_depth` and `exclude_projects`. `WorkspaceConfig.projects` was parsed and no loader consumed it.
2. **The mixed onboarding.** `perform_full_onboarding` in src/tools/onboarding.rs took its project list from `ctx.agent.discovered_projects()`, which describes the default (home) workspace. Its `root` came from the workspace pin. So the home project list was written into the nested repo's `.codescout/workspace.toml`.

A third defect surfaced during the fix (friction F-200 in docs/trackers/bug-fix-session-log.md): `Workspace::memory_dir_for_project` built a member's memory path from the parent workspace root, so a member that is its own git repo kept its memory in the parent.

## Evidence
### 1. `[[project]]` entries ignored
Measured 2026-10-28. The entries were present in the file (`grep -c thecrew` → 5) while `list_projects` showed the five original projects, after each of the three restarts above.

### 2. Doctor treats declared roots as meaningful
src/librarian/tools/doctor.rs:3229-3243: an absolute `[[project]] root` is flagged ("Sub-project roots are relative to the directory owning this file ... Cross-repo grouping belongs in an [[umbrella]], not a [[project]]"). Umbrellas only group librarian docs (reported by a subagent from src/librarian/workspace.rs and src/librarian/tools/scope.rs; not re-read).

### 3. Onboarding under a workspace pin
Measured 2026-10-28. Contents of the nested repo's `.codescout/workspace.toml` after the call: `[workspace] name = "script.module.thecrew"` followed by `[[project]]` ids kodi, xbmc, addons, libUPnP, packaging (the Kodi workspace). `git status` in the nested repo: ` M .gitignore`, one added line. The directory was removed afterwards.

### 4. Git-aware features (subagent read, not re-read)
`last_indexed_commit` / `git_sync` use `Repository::discover(root)` of the project root (src/index_state.rs:259-260, 317 as cited), so commits in a nested repo never register against the parent's index. `dirty_files` is an in-memory set and is not git-based.

### 5. Library route

Read 2026-10-29. src/tools/semantic/semantic_search.rs:633-639 returns `"library scope is not yet supported by the Qdrant retrieval stack"` for `scope="lib:<name>"`. The error names tracker row L-12 in docs/trackers/2026-05-07-legacy-retrieval-removal.md, so the code gap is already tracked there. The manual page docs/manual/src/tools/library-navigation.md lines 112-126 still says `semantic_search` with `scope: "lib:<name>"` works. The manual drift is the open part and is not filed as its own bug. The `.gitignore` edit comes from src/memory/mod.rs:92 and `ensure_gitignored` at :111 (read).

## Hypotheses tried
1. **Hypothesis:** roots outside the workspace root are rejected. **Test:** first `../kodi-refs/...` roots, then in-tree `remote-fixes/...` roots. **Verdict:** rejected. Both failed the same way.
2. **Hypothesis:** the server caches the workspace across re-activation. **Test:** `/mcp` reconnect and a full Claude Code restart. **Verdict:** rejected.
3. **Hypothesis:** discovery is manifest-driven and ignores `[[project]]`. **Test:** read src/workspace.rs. **Verdict:** consistent with the code; not tested by adding a manifest.

## Fix

Chosen: `[[project]]` is the contract; no separate `[[member]]` table.

- **Part A, `711b8c3a4`:** `Agent::discovered_projects_at(workspace_override)`; `perform_full_onboarding` now reads the pinned directory's projects, not the home workspace's.
- **Part B, `0d95ee8bf`:**
  - `merge_declared_projects` (src/workspace.rs) adds declared entries to the discovered list. A discovered root wins. Unsafe or missing roots and unusable ids are skipped with a warning. Empty `languages` fall back to a directory scan.
  - `resolve_projects` (src/agent/mod.rs) is the one loader used by `Agent::new` and `Agent::load_project_resources`.
  - `member_memory_dir` (src/workspace.rs): a member with its own `.git` keeps memory in `<member>/.codescout/memories`. `memory_dir_for_project` and both onboarding loops use it.
  - Manual: "Declared projects and discovered projects" in docs/manual/src/concepts/multi-project-workspace.md.

Still open, not fixed:
- Per-member git identity for indexing. `resolve_head_sha` and `probe_has_git_remote` use `Repository::open(root)`; src/index_state.rs:260 uses `discover(root)`. Not verified for a member inside a parent repo.
- Onboarding a nested repo still appends to that repo's own `.gitignore` (src/memory/mod.rs:92). Judged acceptable.
- `semantic_search(scope="lib:<name>")` returns "library scope is not yet supported by the Qdrant retrieval stack" while the manual says it works. Separate issue.
- Whether the Kodi checkout gitignores `.codescout/`, and whether the `ignore` crate honors `.git/info/exclude` for the walk, are not verified.

## Workarounds
- Activate the nested repo by absolute path with `read_only=false`, onboard and index it, then re-activate the home project. Not tested. Check the new `.codescout/` for the mixed content shown in Evidence 3 first.
- `library(action="register", ...)` gives `symbols` for it, not `semantic_search`.
- Commit in the nested repo with `run_command(cwd="remote-fixes/<repo>")`.
