## F-1 — Guards correct, tested, and unbound to their call sites

**Observed:** Task 7 review, and again in Task 8's brief as a standing instruction.

**Expected:** `guard_sparse` and `guarded_api_key` were both implemented correctly and both had passing unit tests that died when the guard body was deleted.

**Got:** nothing bound either to `from_env`. Replacing `guarded_api_key(url, key)` with the raw `config.api_key.clone()` survived the entire 3505-test suite — and that mutation *is* a project.toml key sent in cleartext to `http://embed.example.com`. Deleting `guard_sparse(&config, lite)?` also survived, which is the silent dense degradation the guard exists to prevent.

**Probable cause:** unit-testing a guard proves the guard works; it says nothing about whether the code path invokes it. The two questions look identical and are not.

**Fix:** extract the wiring into a callable seam (`build_embedder`) so the guards sit inside something a test can invoke, then mutate the *call*, not the function.

**Severity:** high — one of the two mutations is a credential leak.

**Status:** fixed-verified — both call-site mutations now kill named tests.

## F-2 — A guard whose operands defaulted to each other

**Observed:** Task 8 review.

**Got:** the plan specified `self.config.model_dim.unwrap_or(index_dim as usize)` compared against `index_dim`. With `CODESCOUT_MODEL_DIM` unset — documented as "the model is the authority", i.e. the common case — the left operand *becomes* the right one and the comparison can never fail. `unwrap_or(0)`, which would break search for every unpinned user, left all 102 retrieval tests green.

**Probable cause:** the expression reads as a sensible default. Its inertness is only visible when you ask what the two sides are in the unpinned case.

**Fix:** compare the index against the model's real dimension; fall back to a config value only where the model's dim is genuinely unknowable (remote backends).

**Severity:** high — inert in precisely the migration the feature exists to enable.

**Status:** fixed-verified.

## F-3 — The plan mandated a test pattern the crate bans

**Observed:** Task 6, by the implementer.

**Got:** the plan's Global Constraints said env-mutating tests use `EnvGuard` + `#[serial]`. `docs/conventions/test-env-isolation.md` bans that pattern crate-wide (post-`a656f8cec220d347`) and names the alternative. The plan repeated the instruction in three places.

**Probable cause:** written from memory of the convention rather than from the convention. Memory `conventions` still carried the older form.

**Fix:** resolve env once at the edge into a struct, pass it inward, test the merge as a pure function. Corrected in the plan at `893ade0e`.

**Severity:** high — it would have propagated to every remaining task.

**Status:** fixed-verified.

## F-4 — A fix for one Critical introduced another

**Observed:** Task 8, round 2.

**Got:** the round-1 fix for the inert guard (F-2) introduced `known_dim()`, which returned `Some(0)` for a remote-resolved backend — `RemoteEmbedder::dimensions()` is 0 until the first embed. `Some(0).or(pin)` short-circuits, so an operator pin could not rescue it, and the guard then errored on every query, self-sustainingly: it runs before the embed that would populate the dimension. A permanent wedge.

**Probable cause:** two nearly-identical predicates one line apart. `build_embedder` selects the adapter on `embedder_url.is_none()`; `backend_is_local` additionally requires a `local:` prefix. The new code's comment assumed the second.

**Fix:** translate the sentinel at the boundary (`Some(d).filter(|d| *d > 0)`).

**Severity:** high. Notably it landed in the exact branch whose mutation had *survived* in the same review — an uncovered branch is where the next bug lands.

**Status:** fixed-verified. The same sentinel gap was later found in the sibling `new()` by the final whole-branch review and fixed there too.

## F-5 — "The compiler found every call site" is only true for what you compiled

**Observed:** Task 6 review.

**Got:** the deliberate signature break was supposed to make the compiler enumerate every `RetrievalClient::from_env` caller. It enumerated 14. `tests/retrieval_e2e.rs` is `#![cfg(feature = "retrieval-e2e")]`, which none of the gate runs enabled, so four more sites went unseen and the branch did not compile under that feature. Real count: 18.

**Probable cause:** a green gate is evidence about the configurations it ran, and feature-gated code is invisible to configurations that exclude it.

**Fix:** the four sites, plus `cargo check --features retrieval-e2e --all-targets` in CI's feature-check job. Archived bug `0863519e142b71bc` is the same failure for `server-stack`.

**Severity:** high — this is the fifth instance of the class on this branch alone.

**Status:** fixed-verified.

## F-6 — Tests green only because of this machine's ambient environment

**Observed:** Task 6 round 3, and again in Task 9's own first draft.

**Got:** `from_env_and_project_none_root_has_no_embeddings_section` passed only because this host exports `CODESCOUT_EMBEDDER_MODEL_NAME` and `CODESCOUT_EMBED_MODEL` but *not* `CODESCOUT_EMBEDDER_MODEL`. On a host exporting the latter it fails. Separately, Task 9's status test initially checked only `CODESCOUT_EMBEDDER_URL` and missed the `CODESCOUT_EMBED_URL` sibling family — the same two-families footgun the task exists to document.

**Probable cause:** a test that reads process env has as many hidden inputs as the developer's shell has variables.

**Fix:** express against the pure seam with an explicit `EmbedEnv::default()`. Verified immune by exporting the variables that would have broken it.

**Severity:** med — never wrong in CI, wrong on some contributors' machines.

**Status:** fixed-verified.

## W-1 — Break the signature so the compiler enumerates, not the plan author

**Pattern:** when threading a new input through a widely-called constructor, change the signature rather than adding an optional variant. Every call site then fails to compile until someone decides what to pass.

**Counterfactual:** my brief's table listed 7 call sites. The compiler surfaced 14; a later review found 18. With an optional second constructor, the 7 I missed would have silently kept env-only behaviour — including `sync_project`, the CLI the session-start hook invokes, which is exactly the site that shipped dead in the index-state-sidecar incident this project already records.

**Impact:** high. **Status:** validated.

## W-2 — Mutate the call site, not just the function

**Pattern:** a guard's unit test proves the guard works. It does not prove the code path calls it. Delete each call site in turn and confirm a *named* test dies.

**Counterfactual:** without it, three separate things on this branch were deletable with a green suite — `guarded_api_key`'s invocation (a credential leak), `guard_sparse`'s invocation, and the entire project-config read that Task 6 exists to add (3647 tests still passing).

**Impact:** high. Promoted into every brief from Task 5 onward. **Status:** validated.

## W-3 — Verify constants against the library's own registry, never a value we produced

**Pattern:** to check that hardcoded model parameters are right, compare against the library's own source of truth — not against a golden output generated by our implementation.

**Counterfactual:** a golden vector produced by `from_dir` would bake in whatever pooling error it was meant to detect. The hub-vs-dir parity test escapes the circle because the hub path derives pooling/quantization from fastembed's registry and never consults our constants. Measured: under both pooling mutants, only the parity test died — the shape test survived, because a wrong pooling still yields a deterministic, non-zero, 384-d vector.

**Impact:** high. **Status:** validated.

## W-4 — Briefs that demand evidence let implementers overrule the controller

**Pattern:** require mutation evidence and pasted output rather than assurance, and state that a measurement beats an instruction. Then implementers correct the plan instead of transcribing it.

**Counterfactual:** six plan defects were caught this way — a banned test pattern, an inert guard comparison, a false `strip_prefix` rationale, a registry assertion comparing two literals, a single-fixture mutation test that could not discriminate, and a `#[test]` + `block_on` combination that panics against `spawn_blocking`. Each was caught because the brief asked for a dead mutant, not a green run. The implementer that pushed back on the single-fixture instruction traced the short-circuit by hand and was right.

**Impact:** high. **Status:** validated.

## F-7 — `env -i` is not hermeticity when the program re-reads config from disk

**Observed:** 2026-08-13, first end-to-end probe of the local ONNX path against the
release binary.

**When:** Verifying that a `local-dir:` model actually embeds offline. The run was
launched under `env -i` with only `HOME`, `PATH`, and three explicit `CODESCOUT_*`
variables, and was believed hermetic on that basis.

**Expected:** configuration limited to what the command line passed.

**Got (scouted reality):** `main.rs` calls `load_startup_env`
(`src/config/global.rs:118-154`), which reads `~/.config/codescout/.env` **from disk** —
on this host a symlink to the repo's own `.env.amd`. Dotenv precedence is "already-set
wins, unset keys are filled", so the url I had scrubbed was silently restored, and
`build_embedder` then discarded my `local-dir:` model in its favour. The run exited **0**
and reported `added=5` — indistinguishable from success. The only tell was the stored
`vec0` width: `FLOAT[768]`, the remote model's, from weights that were never loaded.

**Probable cause:** treating a process-level env scrub as equivalent to configuration
isolation. `tests/cli_artifact.rs:18-24` already documents the correct escape
(`CODESCOUT_ENV_FILE` pointed at a nonexistent path) — the knowledge existed in the repo
and was not consulted before trusting the result.

**Workaround / fix:** `CODESCOUT_ENV_FILE=<nonexistent>` makes `load_startup_env` a
no-op. With it, the same command logged `local weights: descended into the sole snapshot
directory`, built `FLOAT[384]`, and stored 5 rows in 38 ms with no network.

**Severity:** high — not because of lost time (minutes) but because the failure mode was
a **confident wrong conclusion**. Had the dimension not been checked, this session would
have reported "local ONNX path verified end-to-end" on the strength of a run that never
loaded the weights. It is the reconnaissance substrate rule (read what world the tool
read, not just its verdict) failing in the one place it was most needed.

**Status:** fixed-verified — and it paid for itself: chasing the wrong dimension is what
surfaced the real defect, now `docs/issues/2026-08-13-url-silently-overrides-local-dir-model.md`,
fixed at `38e0980b`.

## F-8 — The first fix draft was too wide: the DEFAULT model carries the rejected prefix

**Observed:** 2026-08-13, full-suite run after implementing the url/local-dir conflict guard.

**When:** The guard was written to reject a url alongside any `local:` **or** `local-dir:`
model — which reads as obviously correct, since both name in-process ONNX.

**Expected:** a guard on a contradictory configuration touches only contradictory configurations.

**Got:** `agent::tests::memory_embedder_is_built_from_the_shared_code_embedder` failed.
`default_embed_model()` **is** `"local:AllMiniLML6V2Q"` (`src/config/project.rs:384-386`),
so "url configured, model left unset" — an ordinary remote deployment — arrives carrying a
`local:` prefix the operator never chose. The guard would have rejected every such setup.

**Probable cause:** reasoning about the model string as though it always reflects operator
intent. It does not: it is the result of a three-way merge whose last fallback is a constant
that happens to name a local backend.

**Workaround / fix:** narrowed to `local-dir:`, which has no default and is therefore
unambiguously intent. The residual — a url still silently beating an explicitly-chosen
`local:` — is recorded in the bug file's Resume rather than hidden, and
`build_embedder_accepts_a_url_with_the_defaulted_local_model` asserts its own premise so
that changing the default forces a re-derivation.

**Severity:** med — caught by an existing test before it could ship, which is the system
working. Worth logging because the wrong version was the *intuitive* one, and because the
test that caught it did so only incidentally (it builds from a root-less config).

**Status:** fixed-verified — `38e0980b`.

## W-5 — Exercise the shipped binary end-to-end, not only the suite

**Observed:** 2026-08-13, verification pass over a branch that was already reviewed,
merge-approved, and green.

**Pattern:** After the suite passes, run the actual release binary through the actual user
journey in an isolated sandbox, and **verify the artifact it produced** (here: the stored
`vec0` dimension) rather than its exit code.

**Counterfactual:** 3701 passing tests, a clean clippy, and a whole-branch review that said
"merge as-is" could not see that `guard_local_model_with_url`'s predecessor guard was
unreachable from the retrieval path — because the crate-level test of that guard passes,
and nothing asserted it at the seam. The feature's core safety property (a restricted host
does not touch the network) was inverted, and the observable signature of the failure was
**exit 0 with no warning**. One binary run found it in minutes. Without this pass the branch
ships with its headline guarantee failing open.

**Confirming data points:**
1. This session — the url/local-dir defect, invisible to the suite, obvious to the binary.
2. F-1 / W-2 (same work stream) — guards deletable with the suite green; same root shape,
   found by mutation rather than by running anything.

**Impact:** high — it is the difference between "the tests pass" and "the feature does what
it promises".

**Promote-when:** a second work stream finds a seam-level defect this way. At two datapoints,
promote to CLAUDE.md's ship sequence as an explicit step: *before integrating a
behaviour-bearing branch, run the release binary through the user journey and verify the
artifact it produced, not its exit code.*

**Status:** validated — single strong datapoint, defect found and fixed at `38e0980b`.
