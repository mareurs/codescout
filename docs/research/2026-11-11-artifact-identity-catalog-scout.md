## 0. Spec vs code: mismatches and gaps (read this first)

M-1. Schema version is 14, not 13. `MIGRATION_VERSIONS = [4, 5, 9, 10, 11, 12, 13, 14]` (src/librarian/catalog/mod.rs:138); the v14 block adds `artifact_chunk.embedded_input_hash` and stamps 14 (mod.rs:500-517). v13 (mod.rs:468-497) retired `artifact_vec`. Baseline stamps 1,2,3,6 (mod.rs:136); v7/v8 are column-only (mod.rs:299-317). The spec does not state a number; your brief did.

M-2. The frontmatter `id:` is NOT stamped by the indexer. It is written by `doc(create)` (create.rs:437 mints, create.rs:469 `id: Some(id.clone())`), re-written on move (mv.rs:389 mints the new id, mv.rs:406 calls `repair_frontmatter_id`, defined mv.rs:~719-810, uses `frontmatter::replace_scalar_line(.., "id", ..)` at mv.rs:784), seeded by `doc(update)` when a file lost its frontmatter (update.rs:595-602), and rewritten by `doctor fix=repair_frontmatter_id` (doctor.rs:2288-2361, calls `mv::repair_frontmatter_id` at doctor.rs:2343). `index_repo_sync` never writes a file. Consequence: only files made through `doc(create)` carry an `id:` (other files have none; `frontmatter::Frontmatter.id` is `Option`, frontmatter.rs:14-17; `RESERVED_KEYS` includes "id", frontmatter.rs:58-67).

M-3. A core-tool guard depends on the stamped `id:` and on the catalog's augmentation table, and the spec's Removed list does not mention it. `src/util/librarian_guard.rs` (445 prod lines) refuses `edit_file` / `read_file` / `read_markdown` on a "librarian-managed" file: `guard_not_librarian_managed` (librarian_guard.rs:49) is called from src/tools/read_file.rs:200, src/tools/edit_file/mod.rs:862 and src/tools/markdown/read_markdown.rs:891. "Managed" = a stamped 16-hex `id:` (`is_librarian_artifact`, librarian_guard.rs:294; `is_librarian_id`, :429; used at :140) OR the catalog says the path carries an augmentation (`AugmentedArtifactOracle`, librarian_guard.rs:72; implemented by `CatalogAugmentationOracle`, adapter.rs:43-67, keyed `artifact_id_from_abs`, adapter.rs:57; installed adapter.rs:70-75). A second hook, `src/util/librarian_sync.rs` (93 prod lines) lets `edit_file` re-sync a row after a direct frontmatter edit: `CatalogFrontmatterSyncer` (adapter.rs:85-165, keyed `artifact_id_from_abs` at adapter.rs:106, `upsert_and_mint_slug` at adapter.rs:162), installed adapter.rs:167-170. Removing the `id:` stamp and params-as-store removes the guard's two signals with no replacement named in the spec.

M-4. `catalog_meta` is not named anywhere in the spec but holds operational state that is not derivable from a commit: gc settings (`gc_grace_days`, `last_reconcile_at`, gc.rs:12-120), one reindex-progress row per running pid (reindex_progress.rs:51-147), audit host id / previous-host chain / shard watermarks (audit/host.rs:273-356, audit/shard.rs:162-228, 703-719), the embed-error marker (reindex.rs:779-784, read find.rs:477), and the chunk backfill cursor (indexer.rs:1636). Spec G1 ("catalog holds nothing that cannot be rebuilt") needs an explicit carve-out for cache / operational state, or a separate machine-state store.

M-5. Embedding vectors are not a content-hash cache today; the spec assumes they are. Reuse is intra-artifact only: `replace_chunks` matches by `(chunk_ix, content_hash)` then by `content_hash` within ONE artifact (catalog/chunk.rs:416-470). Vector rows die with their chunk row through trigger `artifact_vec_v2_cascade_delete` (mod.rs:434-441), and chunk rows die with the artifact row (FK cascade). The Qdrant side is worse: collection name = `artifact_chunks_<basename>_<artifact_id_from_abs(project_root)>` (artifact_store.rs:116-130), so relocating a checkout changes the collection; points carry payload `project_id`, `artifact_id`, `chunk_id`, with a keyword index on `artifact_id` (retrieval/artifact.rs:78, :133-143). The closest existing content-keyed value is `artifact_chunk.embedded_input_hash` (v14, chunk.rs:643-690: hash of title + composed text), which is exactly what a rebuild would reuse.

M-6. A third citation grammar exists on the WRITE path, besides link_scan's two shapes. `resolve_cite_ref` (catalog/augmentation.rs:2457-2540) accepts a 16-hex id, `<slug>:<local>` (validated against the destination's params collection), or a rel_path suffix; `append_entry cites` stores the result as `entry_cite` rows with `origin='write'` (augmentation.rs:985). The spec's Removed list names "the two-shape `entry_cite.dst_ref`"; the write-path resolver, rekey's `dst_ref LIKE` rewrite (rekey.rs:659-690) and gc's rehome `UPDATE entry_cite SET dst_ref` (gc.rs:470) all depend on the same shapes.

M-7. The indexer REFUSES to index a linked worktree (indexer.rs:385-402; test `index_repo_sync_skips_linked_worktree`, indexer.rs:5143). Spec: "A worktree is a checkout. Its catalog view is built from its own files." That guard has to go and something has to say when a worktree is indexed: today reindex is manual only (entry points below), and no automatic caller exists in src/ (companion-plugin hooks: not read).

M-8. `link_scan::extract` cannot simply be deleted. Plan A's own `identity/index.rs` imports `link_scan::extract::entry_sections` (index.rs:24, :39). Doctor uses `extract_memoized` / `entry_sections_memoized` / `CitationKind` at 8 `use` sites (doctor.rs:4401, 4583, 4744, 5103, 5264, 5394, 5515, 5996) plus the memo scope at doctor.rs:964; `catalog/augmentation.rs:2679` (`body_defined_indices`) and `tools/context.rs:141` call it for definitions and sections. Only the CITATION half (RelPathLink / ArtifactId / CrossRepoToken kinds, `Corpus`, `resolve`, `Outcome`, `entry_dst_ref`) is replaced by `identity::grammar` / `identity::index`. Doctor also mirrors the resolver (doctor.rs:4517 "Resolution mirrors link_scan::resolve::resolve").

M-9. Observations: the ONLY prod writer is a side effect of a `note` event: event_create.rs:497-504 copies `payload.text` into `artifact_observation` after the event insert. So every observation row duplicates a `note` event (rows written by older code paths: not checked). The spec treats observations (57) as a separate state class "as for notes".

M-10. Spec "Frontmatter holds scalars only ... link_scan parses bodies, never frontmatter": `link_scan::extract` already skips frontmatter by byte offset (extract.rs:488-505); but frontmatter still declares id namespaces (`entry_prefix`, read via `librarian_guard::declared_entry_prefixes`, extract.rs:515-517) and `expects_augmentation`, `snapshot_anchor`, `external_prefix`, `entry_high_water_*` (augmentation.rs:1244-1255, 1410, 1701). Those are scalars, so consistent; just note `entry_prefix` is a list-ish value parsed by hand.

M-11. `status_change` history is incomplete in the catalog today: `doc(update patch.status)` records only `field_patch` for BODY writes (update.rs:916-940); a `status_change` event exists only when someone calls `event_create kind=status_change` (event_create.rs:202, 259, 390), `superseded_by` only via `doc(link rel=supersedes)` (link.rs:102). So `state_at` (state_at.rs:94 reconstructs status from `status_change`) is built on 3 events (spec: 3). A git-derived timeline is strictly better, as the spec says.

M-12. `Catalog::open` is not read-only: every open runs `apply_schema`, `run_migrations` and `audit::install` (`open` mod.rs:769-784, `open_in_memory` :790-796, `open_with_workspace` :802-824). The cutover's "old file is kept, read-only, as the recovery source" therefore needs a new read-only open that skips all three; otherwise the new binary writes to the old file (and an older binary reruns its own migrations on it, per the spec's constraint).

M-13. Spec says "`entry_reservation`... partly (frontmatter holds `entry_high_water_*`)". Confirmed and more precise: `allocate_entry_id` takes the MAX of three inputs (body max, `entry_reservation`, frontmatter high-water) and writes the frontmatter mark BEFORE commit (augmentation.rs:1831-1975; doc comment 1795-1830). The table is the within-machine race guard (IMMEDIATE tx). Removing it removes the race guard unless the ledger format makes ids collision-free (per-entry files) or a file lock replaces it.

M-14. Claims in the spec that I verified as matching: ids.rs:17-23 (`artifact_id_from_abs`); classify.rs:6-9 `#[serde(deny_unknown_fields)] RuleFile`; requirements.rs:8-12 (17 of 30 sessions); "reindex deletes a moved file's local history" at indexer.rs:852 inside the cited 810-854 window; "7 tables cascade" (gc.rs:420-439: events, event_edges, artifact_augmentation, artifact_observation, artifact_link [two cols], artifact_chunk, entry_reservation; `entry_cite` hangs off `artifact(slug)` instead); `librarian` cargo feature is gone (no `feature = "librarian"` in src; only an evidence Cargo.toml under docs/trackers/ecc-integration/...).

## 2. The indexer / reindex path

Entry points (all manual):
- MCP: `librarian(action="reindex")` -> `tools/reindex.rs::call` (reindex.rs:280; dispatch librarian.rs:169). It calls `indexer::index_repo_sync` at reindex.rs:457, then `flush_vectors` (:49), `restore_declared_augmentations` (:118), `backfill_commits` (:194), `delete_orphan_repos` (:389), writes the embed-error marker (:779-784), and exports audit shards (:812-816).
- CLI: `reindex_cli` (librarian/mod.rs:599) -> `indexer::index_repo` (indexer.rs:2085, async wrapper with 8-way embed concurrency; called mod.rs:729).
- Backfill-only: `indexer::backfill_chunk_vectors` (indexer.rs:1688) via src/cli/backfill_chunks.rs:99.
