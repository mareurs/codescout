# Industry survey: switching reasoning effort or model during an agent's work

Date of research: 2026-10-14. Scope: vendors, products, open-source tools (areas 1-4 of the brief).
Method: WebSearch, WebFetch (pages opened), no code run. Nothing in the repository was modified.

## How to read the evidence labels

- `read: full page` = WebFetch returned the page text and I read the extraction. The fetch tool summarises with a small model, so numbers were copied from that extraction, not from raw HTML. Where the tool said the page was truncated, I say so.
- `snippet only` = only a WebSearch result summary; I did not open the URL. Treat as a lead, not as a fact.
- `403` = the page refused the fetch; I only know what the search snippet said.
- Model names (Fable 5.1, GPT-6 Astra, Opus 5.5 ...) are copied as the pages state them. They are after my training data and I cannot independently confirm them.
- "vendor" = the seller's own claim. "independent" = a third party with no sales stake. "hobbyist" = a single-author GitHub repo with its own small test.

## 2. What this means for our design

Statements marked (inference) are my reasoning, not something a source said.

### A. Which switching signals are common

1. **User-chosen mode** is the dominant shipped design: opusplan (Plan Mode), Cline Plan/Act, Roo modes, Amp dial, Codex effort picker, Aider architect/editor, Claude Code skill/subagent `effort` frontmatter. No signal inference at all.
2. **Prompt-text classification once per user turn**: Gemini CLI (Flash-Lite classifier), OpenRouter Auto (30 task types), effortless (Haiku/Jev judge), moelahmady/satviksinha/jev-router family, tzachbon hook, Copilot ("task complexity"). The stated reason for per-turn rather than per-request is the prompt cache and, for jev-router, "the model cannot change mid-task".
3. **Outcome-learned from user behaviour**: Cursor Router (next user action as label), GPT-5 router (user model switches, preference rates, measured correctness), Not Diamond (implicit feedback). All three are vendor systems trained on large traffic, none is a rule a single team could copy.
4. **Model-initiated escalation**: Anthropic advisor tool, Amp oracle, Devin Fusion lead. The model decides to ask for help; Anthropic reports executors under-call on coding and a low-effort executor "can stop detecting that it is stuck".
5. **Escalate on a checkable failure**: Anthropic's "run at `low`, re-run failures at `high`" needs a pass/fail signal such as tests. This is the only published policy that is explicitly a quality-gated effort switch.
6. **Cache/cost gating on top of every router**: almost every tool refuses to change *model* when the context is large (jev-router, moelahmady, Not Diamond, Copilot, Devin's no-swap argument). Changing *effort* is cache-safe where the API provides a per-message form: Anthropic beta header `mid-conversation-output-config-2026-07-01`, OpenAI `configuration_update` (GPT-6). jev-effort measured a 99.1% cache hit rate over 470 steps.
7. **Hysteresis and holds** are the common remedy for latency and flapping: Astra-Ares leases (1/2/5/10 steps), jev-effort hold, effort-router "after work starts effort can only go up", agent-router 5-minute cooldown and 8-switch cap, jev-router confidence thresholds (up needs 0.3, down needs 0.6), ratchet policy.

### B. Which have any evidence (and how weak it is)

- **Fixed-effort sweeps (vendor, benchmarked)**: Anthropic's Opus 5.5 SWE-bench Pro table (`low` 87.4%, `medium` 92.8%, `high` 95.3%, `xhigh` 96.7%). This is evidence that effort matters on hard long-horizon coding, but it is for *fixed* effort, not switching.
- **Escalate-on-failure (vendor, benchmarked)**: ~97% at ~$0.17 vs 95.3% at $0.29, with the stated caveat that most of the lift is the second attempt.
- **Per-turn model routing in production (vendor)**: Cursor's 41% and 68% cost cuts with satisfaction held or higher. The quality metric is a user-behaviour proxy, no hidden tests; no mid-turn re-routing.
- **Per-step effort routing (hobbyist)**: jev-effort is the only open tool with an A/B on a per-step design: 24 sessions per effort level, 6 small tasks, tests 12/12 both arms, but the author says Jev "isn't much better than lowering effort manually". effortless (per prompt) 96 runs, 12/12 correct everywhere. Both sets of tasks are small and well specified. Our own S5 calibration found the same ceiling (low passed 16 of 16), so none of these tests can detect a loss at the end of a long run. (inference)
- **Router/classifier accuracy**: Jev 99% vs Haiku 92-93% on effortless's 73 self-labelled cases; JevK5 hard-tier 0.784 on its own public set; independent JevBench puts JevK5 at 33.1% vs Jev 36.7% on 308 sealed decisions. These measure agreement with labels. No source ties a Jev effort decision to a hidden-test outcome.
- **Nothing** found measures per-step effort switching on tasks where fixed `low` fails and fixed `high` passes.

### C. The end-of-run failure mode is documented by the vendor

Our observed losses (3 of 24 at `low`: no full test suite run, or a question asked at the end) match, almost word for word, what Anthropic says about Sonnet 5.5 and Haiku 5.5 at low effort: "can skip verifying a change", "might skip the project's tests", "more likely to stop and check in with the user before it finishes" (low and medium, long agentic tasks). Anthropic also gives two system-prompt paragraphs it says remove these behaviours at `low` "with no measurable change in task quality" (no numbers given). Consequences for the design (inference):
- A per-step router that only reads "what is the agent about to do" and says `low` for easy-looking steps may reproduce this failure at exactly the steps that finalise the work. The final steps (before the agent stops, before it writes the closing answer, before it asks a question) are a different state class and may need a floor (medium/high) or the vendor's verification paragraph, independent of any classifier.
- Cheaper than a router to test first: run fixed `low` with the two Anthropic paragraphs added, against fixed `low` without them, on the same tasks. If the 3 losses disappear, the router's job shrinks to saving tokens in the middle of runs.
- Anthropic's own escalation policy needs a failure signal. In a live run the agent's own test output is such a signal (tests run or not, red or green); the hidden grader is not. (inference)

### D. What nobody (that I found) has built

1. A router whose input includes **completion-state features** (tests run yet? last test result? diff size? is the next action a final answer or a question?) and whose output raises effort at the end. Jev-based routers send prompts, recent replies, or the last 6 tool calls; none of the READMEs I read mention an "about to finish" feature.
2. Any **published A/B of per-step effort routing on hidden-test-graded tasks with a baseline that fails**. Existing A/Bs use tasks where cheap settings already pass.
3. An **independent** (non-seller, non-author) evaluation of Jev or JevK5 as an *effort or model router for coding agents*. All routing uses are community repos; TypeSafe's own use cases list routing but report no routing number. The ecosystem list says it does not verify numbers.
4. A comparison of **typed-decision model vs LLM judge vs plain rules** on the same step-routing task measured by *task outcome*. effortless compares judges on label agreement only. The jev-router author reports that adding more state to Jev lowered its confidence on 3 of 4 prompts (4 prompts, anecdotal), which is a warning for "current state plus what the agent is about to do" inputs.
5. A **Claude Code first-party** automatic effort selector (issues #34874 closed not planned, #43326 open, no Anthropic reply).

### E. Things to verify on our side before trusting the plan (not answered by any source)

- Anthropic's effort doc says a per-message effort change placed after a `tool_result`-only user turn "waits for the next `user` turn with new input". Claude Code's docs say `/effort` mid-turn "applies to the next request". Our memory says the mod's rewrite reaches the wire as `output_config.effort` plus an appended `role: system` pin message. jev-effort reports Claude Code already sends its own effort system message (beta `per-turn-control-2026-07-01`) and the last one wins. A direct wire test with a thinking-token positive control, *inside a tool loop*, is still needed to know that a mid-turn change takes effect. (inference: the sources are in tension, not in contradiction)
- Thinking is smallest on follow-up requests that only process tool results ("can skip thinking ... even at xhigh and max"), so the room for a per-step router to save thinking tokens in the middle of a run may be small; the savings are concentrated at the first request after user input. jev-effort's finding that nearly all of its savings come at `max`, ~1% at `high`, is consistent with this (inference).
- Latency: classifier calls of 250-800 ms (Jev claims 70-500 ms; jev-effort median 601 ms; satviksinha 402-839 ms; JevK5 13-30 ms on a server GPU, ~0.6 s on CPU/M1). At one call per model request that is seconds per task; leases reduce it. JevK5-4B on our hardware has not been measured by any source. Jev's hosted sign-ups were paused 2026-09-22.
- Jev and JevK5 input limits (64k and 16,384 tokens) force a summarised state rather than the full conversation; every tool that works truncates (6 tool calls, ~28,000 tokens, 4,000 characters).
- Anthropic says on Fable 5.1 a model "tends to stay consistent" with its earlier replies written at the previous effort. That statement is for Fable 5.1 top-level changes; whether it applies to Sonnet 5.5 per-message changes is not stated.
