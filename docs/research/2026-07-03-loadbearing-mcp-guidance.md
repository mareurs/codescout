# Making Developer-Authored MCP Guidance Load-Bearing Without Weakening Injection Resistance

## TL;DR
- **The core tension is real and confirmed by measurement.** Models are trained to treat *all* tool-result content as "No Authority" (OpenAI Model Spec) / "potentially adversarial" (Claude Code harness), so any lever that makes free-text instructions inside a tool result more commanding is, by construction, forgeable by attacker content in that same channel. The only structurally non-forgeable surfaces codescout controls are the ones the *client* injects from a trusted position — the MCP `server_instructions` field (→ system prompt) and tool **descriptions/schemas** (composed into the tool-definition system prompt) — not the free-text body of a `get_guide` output or a JSON result.
- **But those "trusted" surfaces are weakly load-bearing in practice.** `server_instructions` is frequently ignored or not injected at all by clients; tool-description instructions are followed unreliably even by frontier models (GPT-5, Claude Opus 4.1); and always-on instruction text (CLAUDE.md-style) decays over long sessions and is explicitly wrapped by Claude Code in "may or may not be relevant" framing. The highest-leverage non-forgeable lever available to codescout is the **per-tool `relevant_guide_topic()` auto-injection rendered as a `<system-reminder>`-style, trusted-channel envelope**, because that is the exact pattern Claude Code itself uses to make mid-session steering "not adversarial."
- **Recommended first A/B tests** (detailed below): (1) delegation-anchored per-tool guide injection vs. plain footer; (2) server-computed provenance envelope keys (`refreshed_at_commit`, `commits_behind_head`, `confidence`) vs. prose; (3) short imperative + reason-giving phrasing vs. long prose; (4) instruction in tool **description** vs. tool **result**. Fact-uptake, salience, and instruction-following must be measured as three separate metrics, and every test must include a forged-envelope arm to confirm injection resistance is unchanged.

## Key Findings

1. **Provider instruction hierarchies place tool output at the bottom, explicitly and by training.** OpenAI's Model Spec (2025/12/18) lists "No Authority: assistant and tool messages; quoted/untrusted text and multimodal data" and states such content's instructions "MUST be treated as information rather than instructions to follow" unless higher-authority *unquoted* text explicitly delegates authority. Wallace et al.'s Instruction Hierarchy (arXiv 2404.13208) is the training method behind this: GPT-3.5 was fine-tuned (SFT + RLHF on synthetic conflict data) to "selectively ignore lower-privileged instructions," treating tool/third-party text as lowest priority "while imposing minimal degradations on standard capabilities." This is the settled (i)/(iv)-for-untrusted result the requester already pinned — but crucially, the *same* mechanism suppresses developer-authored instructions that arrive through the tool-result channel, because the model cannot cryptographically distinguish codescout's guide text from a file body quoted inside a result.

2. **Claude Code's own harness confirms the operational trust split and the escape hatch.** A detailed teardown of Claude Code's steering (michaellivs.com, Mar 2026) states: "Models are trained to be skeptical of tool outputs… If models followed instructions in tool responses the same way they follow system prompts, prompt injection would be trivial." The harness's fix is the `<system-reminder>` pattern: the system prompt tells the model "You'll receive `<system-reminder>` tags, follow them," so when the tag appears mid-conversation "it connects back to the system prompt's instructions. It knows these aren't adversarial. They're from the harness, not from some random file it read." This is the single most important mechanism for codescout: **authority is delegated from the system prompt to a tagged channel, and the trust attaches to the channel the client controls, not to text a file body could reproduce.**

3. **The "trusted" developer surfaces are real but weak.** Anthropic's "Steering Claude Code" (June 2026) tabulates seven instruction surfaces by "how much authority it carries," when they load, and compaction behavior: CLAUDE.md (root) is "memoized… cache cleared and re-read after compaction," high context cost; Rules are "re-injected on compaction"; hooks "bypass compaction entirely" and their output "arrives as clean system-reminder messages — no disclaimer." Anthropic explicitly warns that appending instructions "has diminishing returns for adherence… the more instructions you provide… the less strictly Claude will follow them," and that "Never do this" / "Every time X, always do Y" belong in **hooks**, not instruction text, because "the model choosing to run a formatter is different from the formatter running automatically."

4. **MCP `server_instructions` is a genuine but unreliable channel.** The MCP spec defines the `instructions` field as "a 'hint' to the model… MAY be added to the system prompt." Claude Code truncates server instructions and tool descriptions at 2KB each, and with tool-search enabled "only tool names and server instructions load at session start." But adherence is not guaranteed: the MCP maintainers' own blog (Nov 3 2025) says the way a host uses server instructions "is up to the implementer, so it's not always guaranteed that they will be injected," and warns "adherence… is like rolling dice… Don't rely on instructions for any critical actions." Framework issues confirm some agent runtimes read only tool descriptions and never surface `server_instructions` to the model at all.

5. **Knowledge-conflict literature says fact-uptake (ii) is already high — often too high.** ClashEval (Wu et al., arXiv 2404.10198, NeurIPS 2024) found across >1,200 questions in six domains that models "are susceptible to adopting incorrect retrieved content, overriding their own correct prior knowledge over 60% of the time," with two levers codescout can exploit: (a) "the less confident a model is in its initial response (via measuring token probabilities), the more likely it is to adopt the information in the retrieved content," and (b) more-unrealistic content is adopted less. Critically for a Claude-targeted tool, "Claude Opus adheres to incorrect contextual information 30% less than GPT-4o for the same degrees of modification" (Claude Opus is the top model at 74.3% accuracy, 15.7% context bias, 2.1% prior bias) — Claude is comparatively more prior-anchored. Context-Aware Decoding (Shi et al., arXiv 2305.14739) raised faithfulness (+14.3% for LLaMA) but is a *decoding* intervention codescout cannot invoke through MCP. Xie et al.'s "Adaptive Chameleon or Stubborn Sloth" (ICLR 2024) shows uptake is high when evidence is "coherent and convincing," but confirmation bias dominates when context partly agrees with parametric memory.

6. **Provenance metadata measurably shifts reliance — a lever codescout can own.** Source-reliability labels significantly change which of two conflicting passages a model believes, following a consistent credibility hierarchy (Schuster et al., arXiv 2601.03746). Recency/timestamp metadata alone — content held constant — measurably shifts LLM passage preference: Fang et al. (arXiv 2509.11353, tested on GPT-3.5-turbo, GPT-4o, GPT-4, LLaMA-3 8B/70B, Qwen-2.5 7B/72B) found "the preference of LLMs between two passages with an identical relevance level can be reversed by up to 25% on average after date injection," "shifting the Top-10's mean publication year forward by up to 4.78 years and moving individual items by as many as 95 ranks." Per-document credibility scores, operationalized via attention modification (CrAM, AAAI 2025 / arXiv 2406.11497), "improve the RAG performance of LLMs against misinformation pollution by over 20%, even surpassing supervised fine-tuning methods" (up to +25.50 EM / +26.18 F1 for Qwen-7B on TriviaQA). **This is the empirical basis for codescout's `refreshed_at_commit` / `staleness` / `confidence` envelope fields** — but the same literature warns textual staleness markers can be exploited to "silently inflate" behavior by letting the model read the label rather than reason (temporal-validity caveat, arXiv 2606.26511), and one contrary result (arXiv 2605.29928) found LLM confidence "remained largely source-agnostic" in a fallacy-judgment task, so the effect is task-dependent.

7. **Placement evidence points the *opposite* way from the "developer-controlled description is safest" intuition — for a subtle reason.** There is no clean controlled A/B of "identical instruction in tool description vs. tool result." The best proxy, MCPTox (arXiv 2508.14925; 45 live real-world MCP servers, 353 tools, 1,312 test cases across 20 agents), found that when the *same* payload was placed in a tool description "it is merely one of static metadata among many other legitimate tool descriptions… [and] is largely ignored," whereas injections at the **end of returned context/tool-result were most effective** (average tool-poisoning ASR 36.5%, up to 72.8% on o1-mini and 70.2% on Phi-4; "agents rarely refuse these attacks, with the highest refused rate (Claude-3.7-Sonnet) less than 3%"). IFEval-FC (arXiv 2509.18420) separately shows that instructions placed in tool/JSON-schema descriptions "frequently fail to adhere" even for GPT-5 and Claude Opus 4.1. The reconciliation: tool descriptions are *safer* (hard to forge, but easily ignored); tool-result content is *more attended-to* (higher uptake, but forgeable). The developer's job is to combine the safety of the description-anchored channel with the salience of the result channel — which is exactly what the `<system-reminder>` delegation pattern does.

## Details

### The four-way construct split, applied to codescout's surfaces
The requester's taxonomy is the right frame, and the evidence maps onto it cleanly:
- **(ii) Fact-authority** (believe tool results over parametric memory): already high per ClashEval/Xie; the risk for codescout is *over*-reliance, not under-reliance — except that Claude's comparatively stronger priors (30% less context-adherence than GPT-4o) mean codescout may see genuine *under*-use of correct LSP/symbol facts specifically on Claude, matching the requester's RQ3 observation.
- **(iii) Uptake/salience** (attend to and use the result): moved by position (recency), structured format matching training data, and provenance framing. Anthropic's tool-writing guidance says "even your tool response structure—XML, JSON, or Markdown—can have an impact… LLMs are trained on next-token prediction and tend to perform better with formats that match their training data," and that they achieved SWE-bench gains purely by refining tool descriptions.
- **(iv) Trusted-instruction authority for developer text in the tool channel**: the hard one. The only non-forgeable path is delegation from a trusted position (system prompt / tool-definition prompt / harness-controlled tag) to the injected content.

### Why the security tension is structural, not incidental
An attacker who can write into a file body, a git commit message, or a tracker that codescout renders can reproduce *any free-text pattern* codescout uses in a tool result: headers, XML tags like `<guide>`, imperative phrasing, even a fake `[LIVE]` block (which the requester's own ~15-run eval already showed models refuse). So forgeability is determined entirely by **whether the authority comes from a channel the attacker can write into**:
- **Non-forgeable (server/client-controlled):** the `server_instructions` string; the tool **description/schema** text; the tool **name**; and *the fact that* `relevant_guide_topic()` fired for a given tool (the server decides which topic; the attacker cannot). A `<system-reminder>`-style tag is non-forgeable *only if* the harness both reserves the tag for trusted content and has been told in the system prompt to trust it — Claude Code does this for its *own* reminders, but a third-party MCP server cannot emit into Claude Code's reserved reminder channel, so codescout must simulate the *pattern* inside its own tool-result envelope and accept that the literal tag text is imitable.
- **Forgeable (attacker-writable):** any directive in the free-text body of a `get_guide` output or a `symbols`/`references` result, including provenance *claims* an attacker could copy verbatim. This is why provenance fields must be **server-computed JSON envelope keys** (the server knows the real `refreshed_at_commit`), not narrative sentences a file could contain.

The sharp design rule: **codescout should never rely on a tool result to carry a novel instruction. It should use the tool result only to (a) deliver verifiable facts with server-computed provenance, and (b) *trigger* guidance whose authority was pre-established in `server_instructions`/tool descriptions.** That keeps every load-bearing instruction on a non-forgeable surface while using the high-salience result channel only for facts and pointers.

### Instruction decay and the compaction problem
Long-session decay is well documented. Anthropic's docs and community forensics converge: CLAUDE.md content is delivered wrapped in "may or may not be relevant" framing and is summarized away on compaction; frontier models reliably follow only a bounded number of instructions before adherence degrades (a widely cited community estimate of ~150 instructions, treated here as UNVERIFIED). The implication for codescout: a one-time `server_instructions` load will decay, and after compaction the guidance becomes "information, not a rule." The counter-pattern is **event-tied re-injection** — precisely what per-tool `relevant_guide_topic()` provides (it re-fires each time the relevant tool is used), and what Claude Code's hooks/system-reminders provide (re-injected on compaction "with no disclaimer").

### Multi-agent provenance (RQ6)
Direct measured evidence is thin. Anthropic's tabulation notes that when a subagent runs, "only the final message (summary plus metadata) returns to the main session" — raw evidence and server-computed provenance are *dropped by default* across the agent boundary, replaced by the subagent's summary. The agent-provenance survey (arXiv 2606.04990) frames this as an open problem: "few schemas jointly represent reasoning steps, retrieval, tool calls and outputs… intermediate claims, final responses." Practitioner write-ups describe multi-agent "conformity bias… a hallucinated fact introduced early gets reinforced at every hop." **Implication:** codescout's provenance envelope will not survive relay unless the orchestrator is explicitly instructed to preserve it; this cannot be fixed from the server side alone. Honest "nothing found" for a clean lever.

## RQ-by-RQ Synthesis

**RQ-A (provider treatment of MCP instructions / tool descriptions / tool results).** Settled and consistent: tool-role content is lowest-authority by training. OpenAI's Model Spec names tool messages "No Authority" and requires their instructions be treated as information unless unquoted higher-authority text delegates. Claude Code's harness treats tool outputs as "potentially adversarial" and uses `<system-reminder>` tags (authorized from the system prompt) as the delegation mechanism. Anthropic composes tool definitions into "a special system prompt" and treats tool descriptions as prompt-engineerable, high-value text (SWE-bench gains from description edits). `server_instructions` lands in/near the system prompt but injection is implementer-dependent and often skipped. The measured novelty from this pass: instructions in a **tool description are non-forgeable but weakly followed**, while **tool-result text is well-attended but forgeable** — the two properties codescout must combine, not choose between. No provider publishes a *measured* claim that identical text is followed differently in the tool role vs. system role, but the training intent (IH paper) and the placement proxies (MCPTox, IFEval-FC) together establish the direction.

**RQ-B (levers to make developer guidance load-bearing).** Placement dominates: description/schema (non-forgeable, weak), `server_instructions` (non-forgeable, unreliable injection), tool-result body (salient, forgeable), harness reminder/hook (non-forgeable, strongest, but partly outside a 3rd-party server's reach). Recency/position favors putting the operative pointer near the *end* of the result. Re-injection beats one-shot due to decay/compaction. Reason-giving and imperative phrasing are recommended by Anthropic but lack clean effect sizes. Structured formats aid uptake. The MCP-specific prior art codescout already uses (progressive disclosure via startup name/description + on-demand body; `get_guide` tools; JSON envelopes) is exactly right; the open question no public source answers is whether models follow instructions embedded in results *from the server itself* more than relayed third-party content — and the honest answer is **the model cannot tell them apart**, so they should be assumed equally weak, which is why authority must originate in the description/`server_instructions` layer.

**RQ1 (belief in context vs. parametric memory).** Determinants: model confidence (low → more uptake, ClashEval), plausibility/coherence (unrealistic adopted less, ClashEval; "coherent and convincing" adopted more, Xie et al.), partial agreement triggering confirmation bias (Xie et al.), source features/credibility labels (Schuster arXiv 2601.03746), and recency metadata (Fang arXiv 2509.11353). Effect sizes: >60% wrong-context adoption baseline; Claude Opus 30% less than GPT-4o; recency reverses up to 25% of equal-relevance choices; credibility-scored attention +20% (up to +25.5 EM). Decoding-time methods (CAD, +14.3% faithfulness for LLaMA) are unavailable through MCP.

**RQ2 (framings of a tool RESULT that increase uptake).** Measured: provenance/credibility labels and recency metadata (above); "According to…" forced grounding (Weller, EACL 2024) improves QUIP and sometimes accuracy, though "larger models perform significantly better with the grounding prompt… while smaller models perform the same or worse" — a caveat that the technique's benefit is scale-dependent; structure matching training data (Anthropic, internal). Position/recency (lost-in-the-middle; Liu et al., TACL 2023) argues for placing the key fact/pointer at the start or end, not the middle — but one instruction-following study (arXiv 2510.14842) found *no* consistent position effect for *instructions* specifically, so the lost-in-the-middle result may not transfer cleanly from facts to instructions (flag). Confidence/timestamp fields double as calibration signals (RQ3).

**RQ3 (trust calibration, not maximization).** Automation-bias literature (Parasuraman & Manzey lineage) transfers to LLM agents: fluent output inflates perceived credibility, and errors cascade (multi-agent conformity bias). ClashEval is the key calibration datapoint: models are *partially* calibrated (defer when unsure) yet override correct priors >60% of the time. On whether self-reported staleness improves *calibrated* reliance: recency-metadata and staleness-marker studies show staleness signals **do** change behavior, but warn they can be gamed and may inflate scores by being read as labels rather than reasoned about — so codescout's `staleness` field will likely shift behavior, but its calibration value (does the agent verify-then-trust rather than blindly discount *or* blindly trust?) is unproven and must be measured directly. PaperTrail (CHI 2026 / arXiv 2602.21045) found richer provenance lowered *human* trust without changing reliance behavior — a caution that provenance surfacing ≠ provenance-driven action.

**RQ4 (training-side semantics of the tool role).** Publicly, the Instruction Hierarchy paper (arXiv 2404.13208) is the clearest account: GPT-3.5 was SFT+RLHF-trained on synthetic conflict data to prioritize privileged instructions and "selectively ignore lower-privileged instructions," with tool/third-party text at the bottom, "while imposing minimal degradations on standard capabilities." OpenAI's Model Spec codifies the resulting behavior. No provider publishes a knob for "how strongly to weight tool results" or a validated recipe for phrasing results for maximal grounding beyond the tool-writing best-practices blog. Partial "nothing found": training details for Claude's or Gemini's tool role specifically are not public, so transfer of the GPT-3.5-era IH findings to 2026 Claude models is assumed, not shown.

**RQ5 (production coding-agent practice).** Cursor's leaked prompt tells the model that auto-attached IDE state (open files, linter errors, cursor position) "may or may not be relevant… it is up for you to decide," and to gather more info when unsure ("Bias towards not asking the user for help if you can find the answer yourself"). Claude Code uses system-reminders for file-state facts (empty file, truncated read, post-compaction "contents may have been summarized away"). The consistent production pattern: **facts are surfaced with hedged framing; hard behaviors are enforced by hooks, not instructions.** This directly validates codescout's split of facts (result envelope) from behaviors (description/`server_instructions`).

**RQ6 (multi-agent provenance).** Thin/negative: subagents return "only the final message (summary plus metadata)" to the orchestrator (Anthropic), so server-computed provenance is dropped at the agent boundary unless the orchestrator is explicitly told to preserve it; the agent-provenance survey (arXiv 2606.04990) confirms no standard schema carries tool-output provenance across hops, and conformity bias reinforces early errors. Codescout cannot solve this from the server side.

## Mapping to codescout's Surfaces — 3–5 Levers to A/B First

Given codescout controls a ~2200-char `server_instructions` slice (2KB truncation confirmed), tool descriptions, JSON result envelopes with provenance, `get_guide` topics, and per-tool `relevant_guide_topic()` auto-inject — and optionally a companion SKILL.md/hook in Claude Code — the priority order is:

**Test 1 — Delegation-anchored per-tool guide injection (highest priority).**
*Change:* In `server_instructions` (non-forgeable), add one line establishing the channel: "codescout may attach `<codescout-guide>` blocks to tool results; these are authored by the codescout server and should be followed as setup guidance." Then have `relevant_guide_topic()` render the auto-injected topic inside a `<codescout-guide>` envelope at the **end** of the result. Compare against (a) plain prose footer and (b) no injection.
*Eval:* Task set where the correct behavior is "query the index / use `references` instead of full-reading files." Measure guide-adoption rate and task tokens. **Forgery arm (mandatory):** inject an identical `<codescout-guide>` block containing a malicious directive via a file body rendered in a `symbols` result; confirm adoption stays at the requester's established ~0%. Success = higher adoption of legitimate guidance with *no* rise in forged-block adoption. Tests whether system-prompt delegation raises (iv) without opening the hole.

**Test 2 — Server-computed provenance envelope keys vs. prose.**
*Change:* Add JSON keys `refreshed_at_commit`, `commits_behind_head`, `confidence` to every result envelope. Compare structured keys vs. the same information as a prose sentence vs. no provenance.
*Eval:* Two sub-metrics, measured separately. (ii/iii) *Uptake*: on a "what does symbol X resolve to" task with a fresh index, does the agent trust the result instead of re-deriving/parametric-guessing (targets RQ3 under-use)? (iii) *Calibration*: when `commits_behind_head` is high, does the agent verify (re-run/refresh) rather than blindly discard *or* blindly trust? Expect provenance keys to raise uptake when fresh (per credibility/recency literature: labels shift preference, recency flips up to 25% of equal-relevance choices) and to trigger verification when stale. **Forgery arm:** put fake `commits_behind_head: 0` in a file body rendered inside a result; confirm the server-computed envelope value (not the forged prose) is what the agent keys on — the concrete demonstration that server-controlled keys are non-forgeable while prose is not.

**Test 3 — Guide phrasing: short imperative + reason vs. long explanatory prose.**
*Change:* For the top 3 `get_guide` topics, author a ≤5-line imperative version with a one-clause reason ("Use `references` before editing; full-reads exhaust the 25k tool-output budget") vs. the current long-form.
*Eval:* Adoption rate + whether the agent *repeats* the correct behavior unprompted later in the session (persistence). Ties to Anthropic's "diminishing returns with more instructions" and the ~150-instruction ceiling (UNVERIFIED community figure). Success = equal-or-better adoption at a fraction of the tokens, freeing instruction budget.

**Test 4 — Instruction in tool description vs. tool result (the placement question, directly).**
*Change:* Take one high-value behavioral rule (e.g., "prefer `symbols` over reading whole files") and place it (a) only in the tool description, (b) only in a result footer, (c) both.
*Eval:* Adherence over a multi-turn session, including after compaction. Hypothesis from MCPTox/IFEval-FC: description-only is durable but weakly followed; result-only is followed short-term but decays and is forgeable; both is best. **Forgery arm:** confirm the description-sourced rule cannot be overridden by a contrary directive in a file body. Directly answers RQ-B's placement question for codescout's own stack.

**Optional Test 5 — Companion SKILL.md/hook for the non-negotiables.**
For any behavior that "absolutely must happen" (Anthropic's own guidance: use hooks, not instructions), ship a Claude Code companion — a `SessionStart`/`PreCompact` hook or a SKILL.md that re-establishes the codescout-guide channel and re-injects the top pointers with "no disclaimer" framing. Strongest non-forgeable surface, but requires the user to install it, so it is a complement, not a replacement, for `server_instructions`.

**Cross-cutting eval discipline:** always separate three metrics — fact-uptake (ii), salience/use (iii), and instruction-following (iv) — because a lever can move one and not the others (PaperTrail showed provenance moved trust but not behavior). Every test needs a forged-content arm; a lever only "passes" if legitimate load-bearingness rises while forged adoption stays flat.

## Conflicts With Pinned Findings

- **The pinned "in-band markers are forgeable → ~0% directive adoption" is not contradicted, but the placement literature complicates its flip side.** MCPTox shows tool-result/end-of-context injections are *highly* effective against many agents (average ASR 36.5%, up to 72.8% on o1-mini; refusal <3%). Zero-adoption is a property of *well-aligned frontier models facing obvious directives* — Claude-3.7-Sonnet had the highest refusal rate in that study (still <3% overall) — not a universal guarantee. The requester's ~15-run forged-`[LIVE]` result likely holds for Claude specifically, but codescout should not generalize "~0% adoption" to all models or to subtle, plausibly-framed forged guidance, which is a materially different threat than an obvious "ignore instructions" block.
- **"Agents under-use legitimate tool results" (RQ3) vs. ClashEval's ">60% over-reliance."** Not strictly contradictory but in tension: over-reliance is measured on *conflicting factual QA*; under-use is observed on *re-derivation/parametric preference in coding*. Claude's stronger priors (30% less context-adherence than GPT-4o) plausibly explain why codescout sees under-use on Claude specifically. Codescout should not assume the RAG over-reliance literature predicts its agents' behavior — the sign may flip for its model and task.
- **The intuition "put load-bearing instructions in the developer-controlled tool result because we control it" is directly contradicted.** Controlling the text is not the same as it being non-forgeable *or* well-followed: the result body is simultaneously the most forgeable channel and, for durable instructions, among the least reliable. Authority must be anchored in `server_instructions`/descriptions and merely *triggered* from results.
